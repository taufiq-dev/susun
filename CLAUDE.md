# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Trowel is a desktop database GUI (SQL editor, table browser, JSON row viewer) built with Electron, React 19, TypeScript and Vite via electron-vite. It is a from-scratch rewrite inspired by Beekeeper Studio. The main-process side (database clients, saved connections, the `window.api` IPC), the app shell (connect screen, workspace layout, tabs in split panes), the query tab, the table tab, the Row panel (the selected row as JSON) and ER diagrams exist; packaging is what's left of the plan.

Build progress, the remaining steps and open decisions are tracked in `PLAN.md`. Read it at the start of a session and tick its checkboxes as steps land. The repo is a git repository on `main`: commit each step as it lands.

## Commands

Package manager is pnpm 11.

```bash
pnpm dev                 # electron-vite dev server + app; renderer has HMR
pnpm dev --watch         # also rebuild/restart on main or preload changes (otherwise restart manually)
pnpm lint                # ESLint (flat config, cached in .eslintcache)
pnpm test                # Vitest, once (pnpm test:watch to re-run on change); tests are src/**/*.test.ts
pnpm typecheck           # tsc on both TS projects; typecheck:node or typecheck:web for one side
pnpm format              # Prettier --write
pnpm build               # typecheck, then electron-vite build into out/
pnpm start               # run the built app from out/
pnpm build:mac           # package with electron-builder into dist/ (also build:win, build:linux, build:unpack)
```

`build:mac` and `build:linux` skip the typecheck (they call `electron-vite build` directly); `build:win` and `build:unpack` go through `pnpm build`. Vitest (`vitest.config.ts`, which repeats the `@shared` alias) covers pure code such as the SQL splitter; the database clients and UI are tested by driving the built app (below).

To run the built app without touching the real userData folder or the login keychain (e.g. when testing saved connections), use `node_modules/.bin/electron . --user-data-dir=<scratch dir> --use-mock-keychain`; add `--remote-debugging-port=9333` to drive `window.api` over the DevTools protocol. A test window behind other windows gets no animation frames or full-speed timers, which leaves Base UI's menus and tooltips half-closed; add `--disable-backgrounding-occluded-windows --disable-renderer-backgrounding --disable-background-timer-throttling`. The window losing OS focus (someone switching apps during a run) closes a grid cell's editor, which looks like a lost edit: send `Emulation.setFocusEmulationEnabled` over that protocol. Base UI menus open on a real pointer press (`Input.dispatchMouseEvent`), not on `click()` from script. Before starting a test copy again, wait until the old one has exited (or kill it): two copies on one `--user-data-dir` block each other's localStorage, and their pages hang. Native dialogs (the save prompt, Open, Save) can't be clicked over that protocol: add `--inspect=<port>` and, from the main process's inspector, replace `require('electron').dialog.showMessageBox` (and `showSaveDialog`, `showOpenDialog`) with functions that answer as the test needs; the main process looks them up on each call.

VS Code: the "Debug All" launch config debugs main and renderer together (renderer attaches on port 9222).

## Architecture

electron-vite builds three targets from `electron.vite.config.ts`, output to `out/main`, `out/preload`, `out/renderer`:

- `src/main/` — Electron main process (Node). `index.ts` wires things up: IPC, the app menu (`menu.ts`) and the first window. `windows.ts` creates the windows: main windows (the connect screen, then a workspace) and the single Settings window, which loads the same page with `#settings` (`main.tsx` renders `SettingsWindow` for it). They load `ELECTRON_RENDERER_URL` in dev and `out/renderer/index.html` when built. A window's background colour follows the OS theme, so a quick resize doesn't flash white. On macOS it has no title bar (`titleBarStyle: 'hidden'`): the page's 40px top band takes its place, with the traffic lights in its first 80px. In the renderer, `FRAMELESS` (`platform.ts`) and the `frameless:` variant (`main.css`) apply only then; the band drags the window (`app-drag`), and anything clickable in it needs `app-no-drag` or it gets no clicks.
- `src/preload/` — runs before the page with `contextIsolation` on and `sandbox: false`. Exposes `window.electron` (the `@electron-toolkit/preload` wrapper, which can send on any IPC channel) and `window.api` (Trowel's own API, typed as `Api` in `src/shared/api.ts`; see below). Types for both live in `src/preload/index.d.ts`, which `tsconfig.web.json` includes so the renderer sees them.
- `src/renderer/` — the React app. `index.html` sets a strict Content-Security-Policy (`script-src 'self'`, no remote connections), so inline scripts and remote resources are blocked until the CSP is changed. `@renderer` aliases `src/renderer/src` (renderer only).

Two TypeScript projects: `tsconfig.node.json` (main, preload, shared, vite config) and `tsconfig.web.json` (renderer, shared, preload `.d.ts`). Code used by both sides lives in `src/shared/` and is imported as `@shared/…` from main, preload and renderer. The alias is defined in all three sections of `electron.vite.config.ts` and in `paths` of both tsconfigs, so a new alias needs the same treatment. Both projects type-check `src/shared/`, so it must not use Node, Electron or DOM APIs.

### Database access and IPC

- Database drivers (`pg`, `mysql2`, `better-sqlite3`) run only in the main process, behind the `DbClient` interface in `src/main/db/client.ts`: one file per database (`postgres.ts`, `mysql.ts`, `sqlite.ts`), and `createClient(config)` in `src/main/db/index.ts`. The config and result types are in `src/shared/types.ts`.
- SQLite runs each session in its own Electron utility process (`sqlite.process.ts`, loaded with electron-vite's `?modulePath` import), because `better-sqlite3` is synchronous and can't interrupt a query. Killing the process is the only way to stop one, and it is immediate; SQLite's journal rolls back an interrupted write the next time the file is opened. So `disconnect` kills the process, and `cancel` kills it and opens the file in a new one, which loses the session's state (an open transaction, temp tables, attached databases, PRAGMA settings); the cancelled query's error says so. Sessions on one file lock each other as separate SQLite connections do: while one holds a write transaction, another's write waits up to better-sqlite3's 5-second busy timeout, then fails with "database is locked".
- `DbClient` contract every implementation keeps:
  - Each client holds one driver connection, so a transaction can span calls.
  - `query` rows are arrays in `columns` order, so duplicate column names survive.
  - Integers that don't fit a JS number arrive as strings, never rounded (Postgres `int8` is always a string).
  - Dates and times arrive as strings, as the database formats them, never as JS `Date`s (which would drop microseconds and read a Postgres `timestamp` in the local time zone): pg type parsers in `postgres.ts` (which also keep intervals and geometric types as text), mysql2 `dateStrings`. SQLite has no date type.
  - A statement that returns no rows gives empty `columns`/`rows` and its affected-row count.
  - Each client attaches an `'error'` listener, since an unhandled driver `'error'` event crashes the main process.
  - `onLost(listener)` says the connection ended without `disconnect` (server closed it, network dropped it, SQLite's process died), before any call in progress rejects. A lost client stays lost: see Dropped connections.
  - `cancel()` stops the running query, which then rejects, and does nothing when none is running. Postgres (`pg_cancel_backend`) and MySQL (`KILL QUERY`) cancel from a short-lived second connection, and their `disconnect` cancels first, since the server wouldn't notice a closed connection until it next sends something. Some interrupted MySQL functions return a value instead of an error: MariaDB's `BENCHMARK()` returns a row (its `SLEEP()` errors, though MySQL documents `SLEEP()` returning 1).
  - `query` keeps at most `ROW_LIMIT` rows (10,000, in `src/shared/types.ts`) and sets `truncated` when the statement returned more; there is no "load more", since that would hold a query (and on Postgres a transaction) open on the session. Postgres reads through `pg-cursor` and closes it at the limit, and SQLite stops stepping, so the database stops too: a SELECT ends early (so a function it calls that changes data runs only for the rows read), while an INSERT/UPDATE/DELETE ... RETURNING has already made all its changes. Their `rowCount` is then null, and `stopped` tells the two cases apart, from the statement's first word (`stopsAtLimit` in `src/main/db/limit.ts`); the results pane says "Stopped after 10,000 rows" or "First 10,000 rows". mysql2 can't stop the server sending rows without killing the statement (which could leave a MariaDB `INSERT ... RETURNING` half done), so MySQL streams every row through the core connection under the promise wrapper, keeps the first `ROW_LIMIT` and counts the rest into `rowCount`. Of a MySQL `CALL`'s result sets, only the first is kept. A Postgres cursor takes exactly one statement (the extended protocol), so `query` there rejects `select 1; select 2`.
- TLS: `tlsOptions(config.ssl)` in `src/main/db/tls.ts` gives both server clients their TLS options. `verify` passes an explicit `ca` list (Node's default list plus the OS store), since a `ca` option replaces Node's list rather than adding to it. Driver quirks it works around: pg reads `PGSSLMODE` unless `ssl` is set (so off is an explicit `false`); mysql2 checks the host name only with `verifyIdentity`, and not at all correctly for an IP host (so MySQL refuses `verify` with one). Connect errors go through `withoutNodeHint`, which drops Node's inapplicable `--use-system-ca` advice.
- Connect errors: both server clients pass a failed connect through `connectError` (`src/main/db/errors.ts`). Where the driver's message is only a code (refused, host not found, timed out, unreachable), it becomes plain words, a blank line, then the driver's message; the connect screen shows the first paragraph as the error and the rest as detail. pg uses `GuardedSocket` (in `postgres.ts`), because on bytes that aren't the Postgres protocol (a MySQL server's port) pg throws inside the socket's `data` handler, which nothing can catch: it would be an uncaught exception in the main process and a connect that never settles. The guard turns it into a socket error.
- Schema: besides `listTables` and `listColumns`, `listColumnsOf(tables)` reads several tables' columns in one query (in the order given; none for a table that isn't there), and `listForeignKeys()` every foreign key in the database (`ForeignKeyInfo` in `src/shared/types.ts`), which the ER diagram uses. Postgres reads `pg_constraint`, leaving out the copies of a key that partitions get, as `listTables` leaves out partitions. MySQL reads `information_schema`; a key may refer to a table in another database, whose `TableRef` then has that database as its `schema` (MariaDB names unnamed keys `1`, `2`, ... per table, so keys are told apart by table and name). SQLite reads `pragma_foreign_key_list`, which names the referenced table as written (its case is corrected to the table's) and leaves out the columns of a key that refers to the primary key (they're looked up, in the key's order).
- Scripts: the query tab splits its SQL with `splitStatements` (`src/shared/split.ts`) and runs the statements one at a time, stopping at the first error, as psql, the mysql client and sqlite3 do. The splitter follows each database's lexical rules (quotes and escapes, comments, Postgres dollar quotes, MySQL `DELIMITER` and executable comments, BEGIN ... END bodies of triggers and routines); `split.test.ts` lists the cases. `DbClient.query` still takes one statement.
- The renderer reaches the database only through `window.api`. New features should not use the raw `window.electron.ipcRenderer`. To add a method:
  1. Declare it in `Api` in `src/shared/api.ts`.
  2. Implement it in the group's `Handlers` object in `src/main/ipc.ts`, with the same signature plus a leading `IpcMainInvokeEvent`. `handle(group, handlers)` registers each method as channel `<group>:<method>`.
  3. Map it in `src/preload/index.ts` to `invoke('<group>:<method>', …)`.
- Handlers just throw on failure. `handle()` returns an `IpcResult` envelope, and preload rethrows it as a plain `Error` carrying only the message, since custom error properties don't survive `contextBridge`. So the renderer sees a clean `e.message`, without Electron's "Error invoking remote method" prefix. An `AggregateError` with an empty message (Node's, when connecting to `localhost` fails on both `::1` and `127.0.0.1`) is reported as its inner errors' messages (`errorMessage` in `src/main/db/errors.ts`).
- Sessions: `api.db.connect(config)` returns a UUID connection id, whose own session (one `DbClient`) the sidebar and table tabs use. `api.db.openSession(connectionId)` opens another session, a new `DbClient` from the same config, and returns its id; `query` and `cancel` take either id. Each query tab opens a session on its first run and closes it with the tab (`features/query/run.ts`), so tabs run side by side, Cancel stops only its own tab's query, and transactions, temp tables and settings stay in their tab. An in-memory SQLite database exists only in its one connection, so `openSession` returns the connection id for `:memory:`. `ipc.ts` keeps connections and sessions in `Map`s; disconnecting closes a connection's sessions too, and a window's connections close when that window closes or reloads.
- Dropped connections: every session (the connection's own and each query tab's) is a `ReconnectingClient` (`src/main/db/reconnecting.ts`) around a `DbClient`, which replaces a lost connection when next used, never in the background, since that would keep waking a serverless database that scaled to zero. A statement is never sent again: one running when the connection went fails. If what ran on the session could have left state on it (`mayKeepState`: anything but plain reads and row changes), the next statement is held back with an error saying what's gone, once, because a new connection isn't the old session (a second half of a transaction would commit by itself). The connection's own session changing is sent to its window (`api.app.onConnectionChanged`), which shows it in the connection bar (`lost` in `store/session.ts`); `reconnects` there goes up each time it comes back, so what failed to load can reload. Short-lived clients (`applyChanges`, a cancel's second connection) use `createClient` directly. Both server clients set TCP keep-alive (`KEEPALIVE_DELAY_MS`), since a network drop sends nothing.
- `registerIpc()` in `src/main/ipc.ts` registers everything and is called from `src/main/index.ts`.
- Messages from the main process to a page (the app menu's commands, settings changes) are the `on...` methods of `AppApi`: preload listens on the channel named in `AppEvents` (`src/shared/api.ts`) and returns a function that stops listening. The main process sends with `webContents.send` on those channels.
- The app menu's File items (New Query `Cmd+T`, Open `Cmd+O`, Save `Cmd+S`, Save As, Close Tab `Cmd+W`) are `AppCommand`s sent to the focused window's page, which carries them out in `src/renderer/src/commands.ts` (listening starts in `main.tsx`, before React renders). Settings… (`Cmd+,`) opens the Settings window. Reload and DevTools are in the View menu only in development, since a reload loses the window's tabs.
- File > New Window (Cmd+N) opens another main window; each has its own connection, tabs and layout.
- Closing a main window (its close button, Close Window, or quitting) is held back and the page is sent `close-window`: it asks about unsaved tabs, then calls `api.app.closeWindow()`, or `api.app.cancelClose()` if the user cancels. A held-back close cancels a quit, so quitting asks one window at a time (`windows.ts`): the first window asked holds the quit, the others wait without asking, and once it closes quitting starts again for the next; a cancel stops the quit. A page that crashed or is loading isn't asked.
- Query files: `api.files.openSql`/`saveSql` read and write `.sql` files through the native Open and Save dialogs. A window can write only to files its user picked in one of them. The save prompt is `api.app.confirmSave`, a native message box (a sheet on macOS) with Save, Don't Save and Cancel and a "Don't ask again" checkbox; it answers 'discard' without asking when the `askToSaveQueries` setting is off.

### Saved connections

- `src/main/connections.ts`, exposed as `api.connections.list/save/remove`. They are stored configs, not open connections: the renderer passes a saved `config` to `api.db.connect`, with its id, which marks it as just used (`lastUsedAt`, for the connection bar's recent list).
- Each connection's library (`src/main/library.ts`): the `.sql` files saved or opened while connected (`api.files.list/readSql/forget`) and the history of its runs (`api.history`, the last 1,000; `features/query/run.ts` adds each finished run). Both are filed under a key: the saved connection's id, or for a connection that isn't saved, its address. Deleting a saved connection deletes its library.
- Stored in `trowel.db` in `app.getPath('userData')` (`~/Library/Application Support/trowel` on macOS), opened in the main process with `better-sqlite3` (`src/main/store.ts`), which is fine for tables this small. Schema changes go in `MIGRATIONS` there, tracked by `pragma user_version`: append a new entry, never edit one that has shipped.
- Settings (`Settings` and `DEFAULT_SETTINGS` in `src/shared/types.ts`) are in the same file, a row per key (`src/main/settings.ts`), exposed as `api.settings.get/set`; a change is sent to every window (`api.app.onSettingsChanged`). A new setting needs only a field and its default.
- The config is JSON without its password, so new config fields (e.g. SSL) need no migration. A new secret field would need encrypting like the password.
- Passwords are in their own column, encrypted with the async `safeStorage` calls, and come back decrypted in `list()`: protected at rest, not hidden from the renderer. `save` throws if no system keychain is available, rather than store a password safeStorage can only obfuscate; a password that can't be decrypted lists as empty.

### Renderer

- No router: `App` shows `ConnectScreen` or `Workspace` depending on the Zustand session store (`store/session.ts`). Open tabs are in `store/tabs.ts`: `tabs` (each `query` with its `sql`, latest `run` and `sessionId` once opened, `table` with its `TableRef`, or `diagram`, an ER diagram of a `TableRef`), `root`, the tree of panes that splits the tab area as VS Code's editor groups do (`store/panes.ts`, pure functions with unit tests: each pane has its tab ids and active tab, each split a direction and its children's sizes), and `focusedPaneId`, the pane New query and the sidebar act on (clicking in a pane focuses it). `features/workspace/Panes.tsx` renders the panes as one flat list keyed by pane id and absolutely positioned from the tree, so splitting, resizing or maximizing never remounts a pane (its editor keeps its undo history, its grid its scroll); each has a `TabBar` (each tab has a right-click menu, shadcn's `ContextMenu`: split, move, maximize, close, close the pane's others or those to its right), and draggable lines between them resize. `maximizedPaneId` makes the focused pane fill the tab area, the others hidden but mounted; focusing another pane restores the layout (a store subscriber enforces it). `shortcuts.ts` has `Cmd+\` (split) and `Cmd+1` to `Cmd+9` (focus a pane). Split copies a tab into a new pane (a query's SQL, or the same table), as VS Code does; "Move to a new pane" moves it. Tabs drag (`store/drag.ts`): onto a tab bar to reorder or move them (`moveTab`), or onto a pane's drop zones (`DropZones` in `Panes.tsx`, a layer over the content while dragging) to move into the pane or split it (`moveTabToSide`). Only each pane's active tab is mounted, and a tab that moves to another pane remounts, so anything a tab must keep (like a query's result) belongs in the store; `features/query/run.ts` writes a run's outcome there, so it lands even if the tab was switched away, and handles Cancel and the tab's session (closing a tab closes its session, which stops its running query). A query tab may be on a `.sql` file (`file`: its path and the SQL as last read or written), which `features/query/files.ts` uses to tell unsaved changes (`isDirty`; a tab not on a file is unsaved if it has any SQL other than its `initialSql`, what a history entry or a table's menu opened it with) and to save. Close tabs through `closeTab` (or `closeTabs` for several, asking once about them all), and before closing them all call `settleUnsaved` (`features/workspace/closing.ts`), which ask about unsaved work (`isUnsaved`: a query tab's SQL, a table tab's changed rows); the store's `close` doesn't. If a router is ever added, use `HashRouter` or `MemoryRouter`, since the packaged app loads from `file://`.
- The workspace's left side is `features/sidebar/Sidebar.tsx`: an activity bar picking a view (Tables, Saved queries, Recent queries; the choice is in `store/layout.ts`; Tables is a tree with a folder for each Postgres schema, which opens and closes, and MySQL's and SQLite's tables are a flat list; a click or the arrow keys select a table, and a double-click or Enter opens it; a table's right-click menu, in `tableActions.ts`, views its data or structure, opens its ER diagram, copies its name, opens a SELECT, and truncates or drops it after a native confirmation (`api.dialog.confirm`, `api.dialog.showError`), building the SQL with `src/shared/sql.ts`, which quotes identifiers for each database), the views (all mounted, the others hidden, so each keeps its filter and scroll), and the connection bar beneath them (`ConnectionBar.tsx`: the connection's name and type, or Disconnected once lost; its menu, shadcn's `DropdownMenu`, disconnects, edits or switches the connection, or reconnects a lost one, in `features/workspace/connection.ts`). The top bar holds only the row panel button. Edit connection, or a switch that fails, closes the connection with a `returnTo` (`store/session.ts`), which the connect screen opens on. `store/library.ts` has counters the Saved and Recent views reload on.
- Code is grouped by feature under `src/renderer/src/features/` (`connect`, `workspace`, `sidebar`, `query`, `table`, `json-viewer`, `diagram`, `settings`); shared primitives (`Button`, `IconButton`, `TextInput`, `Field`, `Segmented`, `DbMark`) are in `components/ui.tsx`, icons in `components/icons.tsx`, from Lucide (`lucide-react`, the icon set shadcn/ui uses): each is named there for what it means in Trowel and given its size, so components import those rather than Lucide directly. The side panels (saved connections, the workspace sidebar, row panel) are `components/SidePanel.tsx`: drag their inner edge to resize, down to a minimum, while the `MainArea` beside them keeps at least 400px; their widths are in `store/layout.ts`, kept in localStorage. A tab row or list of items is one Tab stop whose arrow keys move between its items (`components/roving.ts`): only its current item has `tabIndex` 0.
- Styling is Tailwind CSS v4 (`@tailwindcss/vite`, `src/renderer/src/assets/main.css`). Keep any other CSS inside `@layer`, since unlayered rules override Tailwind utilities. Clickable things show the hand cursor through one base rule in `main.css` (buttons, tabs, switches, menu items, options, labels around radios and checkboxes; not when disabled), so a new control needs no `cursor-pointer`; don't give it `cursor-default` either, which would override the rule. Colours are CSS variables mapped to utilities (`bg-surface`, `text-muted`, `border-line`, `bg-accent`, ...) with light and dark values following the OS theme; use those rather than raw palette colours.
- Each database type has a colour, and `data-db="<type>"` on an element makes it the `accent` inside: the workspace is tinted by its connection's type, the connect form by the selected type.
- Components merge a caller's `className` with `cn` (`lib/utils.ts`: clsx and tailwind-merge), so a caller's utility overrides the component's own for the same property. `IconButton`'s `label` is its accessible name and its tooltip (`tooltip` can say more); `Button` takes a `tooltip` too.
- shadcn/ui components are in `components/shadcn/` (`components.json`: the `base-nova` style, on Base UI, `@base-ui/react`): `context-menu`, `dropdown-menu`, `tooltip` (its `TooltipProvider` wraps the app in `main.tsx`), `switch`, `select` (opening as a list below its trigger: `alignItemWithTrigger` defaults to false). They are copied in and restyled, as shadcn intends: Trowel's colour tokens (shadcn's `accent` is a hover tint, but Trowel's is the database colour, so a menu item's highlight is `bg-ink/10`), 13px text and 28px rows, no open or close animations, `app-no-drag` on popups (they render in a portal, and may sit over the macOS title band), and explicit return types. To add one: `pnpm dlx shadcn@latest add <name>` (the root `tsconfig.json` repeats the path aliases for the CLI), then change its `from "cn"` import to `@renderer/lib/utils`, add any `@base-ui/react` dependency the CLI didn't install, and restyle it the same way.
- The `react-hooks` lint rules include `set-state-in-effect`: load data in an effect with `.then(...)` callbacks guarded by a `current` flag, and re-run it by bumping a counter in its dependencies (see `TableList`), rather than calling a state-setting function from the effect body.
- A table tab (`features/table/`) shows the table's rows (`TableData.tsx`: a page of 100 at a time, sorted and filtered (`FilterBar.tsx`) by the database with parameterized SQL from `src/shared/sql.ts`, run on the connection's own session; with a primary key its cells edit, the changes kept in the store by row key (`edits`) until Save, which `edits.ts` sends to `api.db.applyChanges` as one transaction on a session of its own) or its columns; its view, page, order and filter are in the tabs store.
- The Row panel (`features/json-viewer/RowPanel.tsx`) shows the focused pane's active tab's selected row as read-only JSON in CodeMirror, with folding and a filter by key; `row.ts`, pure with unit tests, builds the JSON. Both grids select the row of the focused cell (`selectFocusedRow` in `grid.ts`), so clicks and arrow keys move it, and write it to the tab (`selectedRow`, `selectRow`). A tab's grid unmounts with the tab, so a new grid selects the row again: a query result's by the row array itself, which stays in the store, and a table's by its id once the page has arrived. A table's selected row shows its unsaved changes and takes new values as the page changes (`onRowDataUpdated`).
- An ER diagram tab (`features/diagram/`) draws a table and those its foreign keys link it to, or every table of its schema (`scope`), with React Flow (`@xyflow/react`) and dagre (`@dagrejs/dagre`) for the layout. `model.ts`, pure with unit tests, picks the tables, sizes their boxes (estimated, not measured, so the layout runs before anything renders; the height is exact), lays them out (dagre left to right, a table left of those referring to it; a rank too tall for the diagram's shape wraps into columns, since many tables referring to one would otherwise make a column too tall to read; unlinked tables in a grid beneath) and works out the opening view (all of it if that's readable, else 80% on its own table). `TableNode.tsx` is a table's box, with invisible handles on the columns lines attach to. Lines end in a crow's foot at the table with the key and a bar at the table it refers to (SVG markers in `DiagramTab.tsx`). Where tables were dragged and the pan and zoom are kept in the tab, so they come back with it. React Flow's stylesheet is imported in `main.css` into the `components` layer, and themed by its `--xy-*` variables (on `.er-diagram`), which it reads before its own defaults.
- Query results use `components/ResultGrid.tsx` (AG Grid Community; modules registered once in `main.tsx`); its theme and cell formatting are in `components/grid.ts`, which the table tab's grid shares. Rows are arrays, so each column reads its value by index. The editor is CodeMirror 6 through `@uiw/react-codemirror`, set up in `features/query/editor.ts`. Both are themed with the app's CSS variables (AG Grid `themeQuartz.withParams`, CodeMirror `EditorView.theme`), so they follow the OS theme and the accent with no reconfiguring.
- One exception to keeping CSS in `@layer`: overrides of AG Grid's own rules, which are unlayered, so a layered rule would lose to them.

## pnpm and native modules

- pnpm 11 only reads auth/registry settings from `.npmrc`; other pnpm settings go in `pnpm-workspace.yaml`.
- `pnpm-workspace.yaml` sets `nodeLinker: hoisted` (flat `node_modules`, which electron-builder and native-module rebuilds expect). Changing it requires deleting `node_modules` and running `pnpm install` again.
- Dependencies with install scripts must be listed under `allowBuilds` in `pnpm-workspace.yaml`, or `pnpm install` fails with `ERR_PNPM_IGNORED_BUILDS` (e.g. add `better-sqlite3: true` when adding it).
- `postinstall` runs `install-electron` (downloads the Electron binary) and `electron-builder install-app-deps` (rebuilds native modules for Electron's Node ABI). `electron-builder.yml` sets `npmRebuild: false`, so packaging relies on that postinstall rebuild; on a `NODE_MODULE_VERSION` error run `pnpm exec electron-builder install-app-deps`.
- Do not read `.npmrc`: a user hook blocks any Bash command that mentions it, because it can hold auth tokens. It is gitignored.
